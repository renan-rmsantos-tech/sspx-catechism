# ADR-003: O vocabulário de classe morta é derivado da folha de referência do `design/`

## Status

Accepted

## Date

2026-07-27

## Context

O defeito de origem desta iniciativa é `className="input"` aparecendo 28 vezes em `frontend/src/pages/admin/admin-page.tsx`. A classe `.input` existe em `design/assets/catequese-ds.css` — a folha de referência do design system — mas **nunca foi traduzida** para o `styles.css` do projeto. Confirmado no build: zero regras `.input` no CSS de produção. Os 28 controles renderizam com o estilo padrão do navegador.

O modo de falha é preciso e reproduzível: alguém leu um nome de classe no documento de referência e o escreveu no código, e nada reclamou.

Duas restrições técnicas moldam a solução:

- **O teste não tem CSS gerado para consultar.** `frontend/vitest.config.ts` não carrega o plugin do Tailwind — só `react()` —, então os testes nunca exercitam a geração de CSS. E no `infra/Caddy.Dockerfile` o `npx vitest run` (linha 13) roda **antes** do `npm run build` (linha 14), então `dist/` também não existe no momento do teste.
- **O portão roda na droplet de produção** (`infra/README.md:244-245`), então compilar CSS dentro do teste tem custo operacional real.

## Decision

**A regra deriva seu vocabulário do próprio design system: extrai os seletores de classe de `design/assets/catequese-ds.css`, subtrai os que `frontend/src/styles.css` de fato define, e proíbe o restante em `className`.**

```
legacyOnly = classes(design/assets/catequese-ds.css) − classes(frontend/src/styles.css)
```

Hoje esse conjunto contém `input`, `btn`, `btn-primary`, `card`, `select`, `textarea`, `field`, `seg-btn`, `list-row`, `num-col` e companhia — e é exatamente o que reprova os 28 controles do admin.

**Dependência de caminho.** O contexto de build já é a raiz do repo (`compose.traefik.yaml:48`), mas o `Caddy.Dockerfile:11` copia apenas `frontend/`. Uma linha de `COPY` passa a trazer `design/assets/catequese-ds.css` para `/design/assets/`, espelhando o layout: como `COPY frontend/ ./` põe o frontend em `/app`, o caminho relativo `../design/assets/catequese-ds.css` resolve igual dentro da imagem e fora dela. O Dockerfile já copia de fora de `frontend/` — o `Caddyfile.traefik` vem da raiz.

## Alternatives Considered

### Alternative 1: Compilar o CSS dentro do teste

- **Description**: O teste invoca o compilador Tailwind sobre `styles.css` e os fontes, e confere cada classe literal usada contra o CSS resultante.
- **Pros**: Verdade fundamental — pega classe morta de qualquer origem, inclusive erro de digitação novo como `className="inptu"`.
- **Cons**: Acopla o meta-teste ao pipeline de CSS, que hoje o Vitest deliberadamente não carrega. Adiciona a compilação ao portão que roda na máquina de produção. E a saída da compilação depende da versão do Tailwind, tornando o teste sensível a atualização de dependência.
- **Why rejected**: Custo operacional e acoplamento desproporcionais ao ganho. O modo de falha real observado não foi erro de digitação — foi cópia de nome do documento de referência, que a decisão adotada pega inteiramente.

### Alternative 2: Vocabulário conhecido, sem build

- **Description**: Toda classe usada precisa ser uma das definidas em `styles.css` (`num`, `eyebrow`, `wordmark`, `display`, `text-muted`) ou ser reconhecida como utility do Tailwind por gramática.
- **Pros**: Rápido, sem build, sem dependência de caminho externo.
- **Cons**: A gramática de utilities do Tailwind v4 é grande — valores arbitrários (`rounded-[var(--r)]`), variantes empilhadas, seletores aninhados (`[&_svg]:size-4`), `has-checked:`, `max-lg:`. Reconhecê-la corretamente é reimplementar parte do Tailwind, e errar produz falso positivo.
- **Why rejected**: O ADR-001 estabelece que regra com falso positivo não entra. Esta abordagem carrega falso positivo por construção.

### Alternative 3: Lista negra escrita à mão

- **Description**: Enumerar manualmente os nomes proibidos num arquivo do projeto.
- **Pros**: Trivial de implementar; sem dependência do `design/` em tempo de execução.
- **Cons**: Envelhece em silêncio — se o `design/` ganhar um componente novo, a lista não acompanha, e a regra passa a mentir por omissão.
- **Why rejected**: Reintroduz o problema que a iniciativa existe para resolver: documentação e código divergindo sem ninguém notar.

## Consequences

### Positive

- Fonte da verdade única: a lista é o `design/`, não uma cópia dele. Se o design system ganhar ou perder um componente, a regra acompanha sozinha.
- Zero falso positivo: só reprova nome que o documento de referência define e o projeto não traduziu.
- Custo desprezível no portão: duas leituras de arquivo e uma diferença de conjuntos.
- A mensagem de falha pode ser precisa — "`input` existe em `design/assets/catequese-ds.css` mas o projeto não a traduziu" ensina o conserto.

### Negative

- Cria uma dependência de caminho entre a suíte do frontend e um diretório fora de `frontend/`, quebrando parcialmente a autossuficiência daquele diretório.
- O `Caddy.Dockerfile` passa a copiar mais um arquivo — uma alteração no caminho de deploy, que foi reconstruído recentemente.
- Não pega erro de digitação de utility do Tailwind, que continua invisível.

### Risks

- **O `COPY` falhar no deploy real e a regra não rodar no único portão que existe.** *Mitigação:* exercitar um deploy real é dependência bloqueante do fecho da Fase 1, antes de qualquer regra ser construída em cima.
- **A extração de seletores errar em CSS complexo** (seletores compostos, `:has()`, aninhamento). *Mitigação:* o fixture plantado obrigatório do ADR-005 do registro de regras cobre isso; e a folha de referência é estável, versionada e não gerada.

## Implementation Notes

- Assinatura: `legacyOnlyClasses(referenceCss: string, projectCss: string): Set<string>`.
- Resolução de caminho relativa à raiz do frontend, para que dev e imagem coincidam.
- Linha nova no `infra/Caddy.Dockerfile`, **antes** do `RUN npx vitest run` da linha 13.
- A função é testada isoladamente com CSS sintético, além do fixture plantado da regra.
