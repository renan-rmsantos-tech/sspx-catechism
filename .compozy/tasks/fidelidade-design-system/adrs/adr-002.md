# ADR-002: A porta são meta-testes Vitest no trilho existente, mais um hook pre-push

## Status

Accepted

## Date

2026-07-27

## Context

O PRD fala em "barrar o merge". Tecnicamente isso não existe neste repo:

- O GitHub Actions está **dormente** por bloqueio no nível da conta (`.github/workflows/deploy.yml:3-6`, confirmado em `infra/README.md:139-144`). O workflow não dispara.
- Não há hook git ativo: sem husky, lefthook, pre-commit ou lint-staged. `.git/hooks/` contém apenas os `.sample` do git.
- Não há ESLint, Prettier, Biome ou stylelint. O script `lint` do frontend é `tsc -b --pretty false` — verificação de tipos, não de estilo — e **não roda em portão nenhum**.
- Os dois únicos portões reais vivem dentro de Dockerfiles e só disparam em `git push production main`: `RUN go test ./...` (`backend/Dockerfile:10`) e `RUN npx vitest run` (`infra/Caddy.Dockerfile:13`).

Duas circunstâncias favoráveis: a guarda de cor literal (`frontend/src/test/color-literals.test.ts`) **já roda dentro do portão de deploy**, então um hex solto já barra publicação hoje; e o repo já tem o idioma de meta-teste estabelecido, incluindo auto-verificação por fixture plantado.

Uma circunstância desfavorável: o portão de deploy roda na própria droplet de produção, competindo por CPU com os apps no ar (`infra/README.md:244-245`). Peso de teste ali tem custo operacional real.

## Decision

**As verificações de fidelidade são meta-testes Vitest, no mesmo trilho da guarda de cor literal, e ganham um hook `pre-push` versionado em `scripts/`.**

Isso produz três pontos de execução, com os mesmos arquivos de teste:

| Onde | Dispara | Barra |
|---|---|---|
| Máquina de quem edita | `npm test` em `frontend/` | nada — feedback |
| `pre-push` | `git push origin` | o push |
| Portão de deploy | `git push production main` → `post-receive` → `docker compose up --build` → `RUN npx vitest run` | o deploy |

O hook fica em `scripts/pre-push.sh`, versionado ao lado do `post-receive.sh` que já mora lá, e é instalado por cópia para `.git/hooks/pre-push` — mesmo procedimento do hook de deploy, documentado em `infra/README.md` §8.

## Alternatives Considered

### Alternative 1: Somente o trilho existente

- **Description**: As verificações entram como meta-testes Vitest e nada mais é criado; barram apenas no `git push production main`.
- **Pros**: Zero infraestrutura nova; nenhum procedimento de instalação por máquina; menor superfície de manutenção.
- **Cons**: O erro só aparece no deploy, e reprovar ali significa um build gasto na máquina de produção. O ciclo de retorno fica longo demais para uma iniciativa cujo trabalho é justamente corrigir divergências em série.
- **Why rejected**: Feedback tardio demais para a fase de correção, que fará dezenas de alterações consecutivas.

### Alternative 2: Hook do Claude Code (`PostToolUse`)

- **Description**: Meta-testes Vitest mais um hook em `.claude/settings.json` que roda as verificações após cada edição de `.tsx`, devolvendo a falha ao agente na hora.
- **Pros**: Pega o erro no instante em que nasce; feedback imediato durante o trabalho assistido.
- **Cons**: Protege apenas contra edição feita por agente — edição manual passa livre. E adiciona um arquivo de configuração que hoje não existe em lugar nenhum do repo.
- **Why rejected**: Cobertura parcial por construção. Pode ser adicionado depois sem conflitar com esta decisão.

### Alternative 3: Resolver o CI antes

- **Description**: Tratar a ausência de CI como bloqueio — destravar o Actions com o suporte do GitHub ou migrar para outro provedor — e só então construir a porta.
- **Pros**: A porta nasceria num lugar convencional, com verificação obrigatória por pull request.
- **Cons**: Depende de terceiro sem prazo. O bloqueio é administrativo na conta e já persiste; a iniciativa ficaria parada indefinidamente.
- **Why rejected**: Dependência externa sem prazo, para um problema que o trilho existente já resolve.

## Consequences

### Positive

- Nenhuma infraestrutura nova de CI: as verificações são coletadas pelo Vitest como qualquer outro teste.
- A guarda de cor literal é absorvida sem mudar de lugar nem de comportamento.
- Reprovar no deploy é seguro: o `post-receive.sh:107-111` faz apenas `git reset --hard` quando o build falha, sem tocar containers — a versão anterior segue no ar, impacto zero.
- Se o Actions for destravado no futuro, o workflow dormente já roda `npx vitest run` e passa a executar a porta sem nenhuma alteração.

### Negative

- O `pre-push` exige instalação manual por máquina, porque o git não versiona hooks. Quem não instalar não é barrado antes do push.
- O portão de deploy continua rodando na máquina de produção; toda regra adicionada ali tem custo de CPU em produção.

### Risks

- **Hook não instalado vira falsa sensação de proteção.** *Mitigação:* documentar a instalação em `infra/README.md` §8, junto do `post-receive.sh`, e tratar o portão de deploy como a rede real — o `pre-push` é conveniência, não garantia.
- **Regras pesadas encarecerem o deploy.** *Mitigação:* toda regra é leitura de arquivo, sem compilação nem renderização; ver ADR-003, que rejeita explicitamente compilar CSS dentro do teste por esse motivo.

## Implementation Notes

- Local das regras: `frontend/src/test/design-fidelity/`, ao lado de `src/test/color-literals.test.ts`.
- `scripts/pre-push.sh` roda `npm test` em `frontend/`; instalação por `cp scripts/pre-push.sh .git/hooks/pre-push && chmod +x`.
- Nenhuma alteração em `compose.traefik.yaml` nem no `post-receive.sh`.
