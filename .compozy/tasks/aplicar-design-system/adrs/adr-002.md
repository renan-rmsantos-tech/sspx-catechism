# ADR-002: Tokens DS nativos como fonte da verdade, com alias shadcn

## Status

Accepted

## Date

2026-07-24

## Context

O tema atual (`frontend/src/styles.css`) segue a convenção shadcn: variáveis `--primary`, `--background` etc. em `:root`, mapeadas para utilities via `@theme inline` do Tailwind v4. O design system Catequese define seu próprio vocabulário de tokens (`--accent`, `--fg`, `--surface`, tríades `--warn/-soft/-ink`, `--gold`…) em oklch com derivados via `color-mix()` (`design/colors_and_type.css`, `design/tokens.css`). O `AGENTS.md` proíbe importar a folha de referência crua — os tokens precisam ser traduzidos para o stack. A questão: qual vocabulário é o primário na aplicação?

## Decision

Declarar os tokens com os **nomes do DS** em `:root` como fonte da verdade (core six, derivados `color-mix`, tríades de estado, dourado, tipografia, espaçamento, raios, sombras, movimento, layout), expô-los no `@theme inline` (gerando utilities como `bg-accent-soft`, `text-warn-ink`, `shadow-2`, `min-h-touch`) e **apontar as variáveis shadcn para eles** como alias derivados (`--background: var(--bg)`, `--primary: var(--accent)`, `--destructive: var(--danger)`…). O fallback sRGB do DS (`@supports not (color: oklch(...))`) acompanha, com os hex sancionados da tabela de conversão.

## Alternatives Considered

### Alternative 1: Nomes shadcn como primários

- **Description**: Manter `--primary`, `--secondary` etc. como vocabulário principal, recebendo os valores do DS, e criar tokens extras só para o que o shadcn não tem (dourado, tríades, surface-2/3).
- **Pros**: Menos variáveis; convenção familiar a quem usa shadcn.
- **Cons**: O vocabulário diverge do DS — cada referência `.jsx`/HTML exige tradução mental (`--accent-soft` → `--secondary`?); risco de deriva visual cresce; metade dos tokens do DS não tem lar na convenção shadcn de qualquer forma.
- **Why rejected**: A tradução quase 1:1 das referências é o principal mitigador do risco de deriva apontado no ADR-001; abrir mão dela para poupar alias não compensa.

## Consequences

### Positive

- As classes das referências (`catequese-ds.css`, `.jsx`) traduzem-se quase diretamente para utilities (`bg-accent-soft`, `text-gold-ink`).
- Componentes shadcn existentes e futuros continuam funcionando via alias, sem retoque.
- Troca de valor de token é um ponto único de mudança, propagada globalmente.

### Negative

- Duas camadas de nomes convivem (DS + alias shadcn) — é preciso disciplina para usar o vocabulário DS no código novo e deixar os alias só para componentes shadcn.

### Risks

- **Alias esquecido** (componente shadcn novo referenciando variável não mapeada) aparece como cor quebrada — mitigado pela conferência visual contra as referências e pela guarda de cor literal.

## Implementation Notes

Reescrita completa do `:root` e do `@theme inline` em `styles.css`; paleta âmbar e `@custom-variant dark` removidas (Non-Goal: sem tema escuro). Tokens não-cor (espaçamento, raios, sombras, motion, `--touch`, `--nav-w`) entram no mesmo bloco e são expostos como utilities quando úteis.
