# ADR-002: Tokens em duas camadas — `--ds-*` como fonte, aliases shadcn por cima

## Status

Accepted

## Date

2026-07-24

## Context

O frontend usa Tailwind v4 (CSS-first, sem `tailwind.config`): o tema vive em `frontend/src/styles.css` como `@theme inline` + `:root` com os hex da paleta âmbar/creme. Todas as telas existentes consomem os nomes semânticos do shadcn (`bg-primary`, `text-muted-foreground`, `border-border`…). O design system define vocabulário próprio em oklch (`--accent`, `--surface`, `--gold`, tríades `--warn/--danger/--info`, derivados via `color-mix()`) em `design/colors_and_type.css` e `design/tokens.css`, e o `AGENTS.md` proíbe importar a folha de referência crua.

Há uma colisão real de nomes: o DS usa `--accent` para o teal de ação; o shadcn usa `--accent` para fundo sutil de hover. Adotar os nomes do DS sem prefixo quebraria silenciosamente os componentes shadcn.

## Decision

`styles.css` passa a ter **duas camadas** no `:root`:

1. **Camada DS (fonte da verdade)** — os tokens de `design/colors_and_type.css` + `design/tokens.css` traduzidos com prefixo `--ds-` (`--ds-accent`, `--ds-surface`, `--ds-gold`, `--ds-warn-soft`…), em oklch com derivados via `color-mix()`, incluindo o bloco de fallback sRGB (`@supports not (color: oklch(…))`) — única exceção hex autorizada.
2. **Camada de aliases shadcn** — as variáveis que as telas já usam apontam para a camada DS: `--primary: var(--ds-accent)`, `--background: var(--ds-bg)`, `--border: var(--ds-fg-line)`, etc.

O `@theme inline` continua expondo os utilities shadcn existentes e ganha os exclusivos do DS (`--color-gold`, `--color-warn`, variantes `-soft`/`-ink`, `--color-accent-press`), as quatro stacks de fonte do DS (sistema puro, zero webfont) e os raios 8/12/16/22px. Espaçamento usa a escala padrão do Tailwind (o `--sp-*` do DS coincide: 4/8/…/64px); alvo de toque de 44px = `min-h-11`.

## Alternatives Considered

### Alternative 1: Só nomes do DS

- **Description**: Abandonar o naming shadcn; `@theme` expõe `--color-accent`, `--color-surface` etc. e todos os usos existentes são reescritos.
- **Pros**: Vocabulário 1:1 com o design system; conferência direta contra `catequese-ds.css`.
- **Cons**: Reescrita mecânica de todas as telas na Fase 0 (antes das ondas); componentes shadcn/base-nova futuros exigem retradução manual; a colisão `--accent` exige renomear de qualquer forma.
- **Why rejected**: Custo imediato alto sem ganho — a camada de aliases dá a mesma fidelidade com re-skin automático das telas atuais.

### Alternative 2: Só nomes shadcn

- **Description**: Traduzir os valores do DS direto para os slots shadcn e criar os extras (gold, warn, info) no mesmo padrão de nome, sem camada DS separada.
- **Pros**: Menos indireção; um único conjunto de variáveis.
- **Cons**: Perde o vocabulário do DS (`accent-soft/-ink/-press`), dificulta auditar contra a folha de referência, e os derivados via `color-mix()` ficariam espalhados pelos slots shadcn sem rastro da fórmula original.
- **Why rejected**: A auditabilidade contra o DS é objetivo do PRD (Goals §2); a camada extra custa pouco e preserva a rastreabilidade.

## Consequences

### Positive

- No instante em que os aliases apontam para `--ds-*`, todas as telas existentes re-skinam para o teal automaticamente — a Fase 0 propaga o visual sem tocar tela alguma.
- Cada valor tem um só dono: mudar um token do DS muda tudo que deriva dele.
- A conferência contra `design/colors_and_type.css` é linha a linha (mesmos nomes, menos o prefixo).

### Negative

- Uma indireção a mais (`bg-primary` → `--primary` → `--ds-accent`) ao inspecionar no DevTools.
- Dois vocabulários coexistem no código (telas antigas usam aliases; superfícies novas podem usar utilities DS) — mitigado por convenção documentada no próprio `styles.css`.

### Risks

- **Deriva entre camadas** (alias apontando para token errado). Mitigação: a tabela de mapeamento vive num bloco único e comentado do `styles.css`; conferência visual da Fase 0 contra `design/ui_kits/app/components.html`.

## Implementation Notes

- A menção a `Inter` (`styles.css:10,56`) sai; entram `--ds-font-display/body/mono/logo` com as stacks de sistema do DS (decisão explícita do design: nenhum webfont).
- `--ds-font-logo` (serifa) só pode ser consumida pelo componente de wordmark — regra inegociável nº 3.
- O gate de CI de cor literal (ADR-005 / TechSpec §Testing) trata `styles.css` como o único arquivo autorizado a conter literais de cor.
