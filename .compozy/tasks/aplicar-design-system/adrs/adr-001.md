# ADR-001: Aplicar o design system via fundação + ondas verticais

## Status

Accepted

## Date

2026-07-24

## Context

O projeto ganhou um design system completo ("Catequese", criado com OpenDesign) em `design/`: tokens oklch, folha de referência CSS, componentes JSX de referência, três shells (auth, catequista, admin) e brand assets prontos. O frontend atual usa uma paleta âmbar/creme oposta ao novo visual, tem cores hex inline (inclusive o verde/vermelho ad-hoc da chamada que motivou o redesign) e apenas 2 componentes compartilhados.

Forças em jogo:

- A aplicação **ainda não foi lançada** — não há usuários para reeducar nem PWAs instalados com ícone cacheado; estados visuais intermediários não incomodam ninguém.
- **Sem prazo rígido** — qualidade acima de velocidade.
- Escopo aprovado é **total**: reskin das telas existentes + superfícies novas do DS (stepper de inscrição, drawer de revisão, calendário litúrgico, gráficos) + marca completa (ícones, manifest, favicon).
- Pesquisa de mercado: adoção tokens-first é a prova de valor mais rápida e reversível; rollouts em fases superam big-bang; a camada de tokens do shadcn é centralizada, então trocá-la de uma vez é seguro.

## Decision

Aplicar o design system em uma **fase de fundação** seguida de **ondas verticais por área da aplicação**:

- **Fase 0 — Fundação**: tokens oklch traduzidos para o tema da aplicação, marca completa (brasão, favicon, ícones PWA, manifest) e biblioteca de componentes-âncora (Button, Chip, Field, AttendanceRow, Sidebar, Drawer, Metrics) adaptada das referências.
- **Onda 1 — Autenticação**: login + trocar senha no shell full-ink, com regras de senha ao vivo.
- **Onda 2 — Catequista**: dashboard + folha de chamada (chip de rede, trilho de progresso, botão "Faltam N").
- **Onda 3 — Inscrição pública**: formulário em etapas (stepper).
- **Onda 4 — Admin**: sidebar agrupada, tabelas, drawer de revisão, calendário litúrgico, gráficos.

Cada onda entrega telas **completas** (incluindo suas superfícies novas) e só fecha ao passar na checklist do `design/SKILL.md`.

## Alternatives Considered

### Alternative 1: Big-bang total

- **Description**: Uma única grande entrega com tudo redesenhado, integrada quando 100% pronta.
- **Pros**: Nunca existe estado visual misto.
- **Cons**: Revisão gigante e difícil de validar; erro de fundação descoberto tarde contamina todas as telas; longos períodos sem nada revisável.
- **Why rejected**: Risco acumulado sem benefício — como o app não foi lançado, evitar estado misto não vale nada.

### Alternative 2: Reskin primeiro, superfícies novas depois

- **Description**: Duas macro-etapas — primeiro só o novo visual nos fluxos existentes, depois as superfícies novas (stepper, drawer, calendário, gráficos).
- **Pros**: Coerência visual 100% mais cedo.
- **Cons**: Toca as mesmas telas duas vezes (ex.: formulário de inscrição re-estilizado e depois refeito como stepper) — retrabalho puro.
- **Why rejected**: Sem prazo apertado, o benefício de "coerência cedo" vale pouco; o retrabalho não se justifica.

## Consequences

### Positive

- Tokens propagam o novo visual globalmente desde a Fase 0, de forma centralizada e reversível.
- Cada onda é um incremento revisável e estável, com critério de saída objetivo (checklist do SKILL.md).
- Superfícies novas nascem dentro da onda da sua área — nenhuma tela é retrabalhada.
- Erros de fundação (tokens/componentes) aparecem cedo, antes de contaminar telas.

### Negative

- Entre a Fase 0 e a última onda, telas ainda não migradas exibem visual "velho sobre tokens novos" (aceitável: sem usuários).

### Risks

- **Componentes-âncora mal calibrados na Fase 0** forçariam retoques nas ondas seguintes. Mitigação: validar os componentes contra as telas de referência (`design/ui_kits/app/*.html`) antes de abrir a Onda 1.
- **Deriva em relação ao design** ao adaptar JSX de referência para o stack real. Mitigação: `catequese-ds.css` e os HTMLs de referência servem de oráculo visual de conferência por onda.

## Implementation Notes

Nível de negócio apenas; detalhes técnicos ficam para o TechSpec. Premissas herdadas do repositório: a tradução dos tokens para o stack (sem importar o CSS de referência cru) já é regra do `AGENTS.md`, assim como as regras inegociáveis (zero cor literal, um primário por tela, alvos de 44px, números tabulares, offline visível).
