# ADR-005: Playwright com API mockada — e2e dos fluxos críticos + screenshots como baseline visual

## Status

Accepted

## Date

2026-07-24

## Context

O frontend tem Vitest + Testing Library (jsdom, thresholds de coverage 80%) e nenhum e2e. O PRD exige paridade funcional após cada onda (incluindo a chamada offline com sincronização posterior), fidelidade auditável ao design e um "baseline visual" de capturas ao fechar cada onda — deixando em aberto onde guardá-lo. O CI atual (`.github/workflows/deploy.yml`) roda `go test` + `vitest run` e não sobe banco/backend para testes de frontend; também não aplica os thresholds de coverage (roda `npx vitest run` cru).

jsdom não exercita service worker, `navigator.onLine` real, IndexedDB de verdade em navegador, nem produz screenshots — exatamente o que a paridade da chamada offline e o baseline pedem.

## Decision

Adicionar **Playwright** (chromium apenas) ao frontend com **API mockada via `page.route`**:

- Um spec por fluxo crítico: login com redirecionamento por papel; troca de senha com regras ao vivo; **chamada offline de ponta a ponta** (`context.setOffline(true)` → marcar → fila visível → online → assert do `POST /api/attendance`); inscrição por etapas com conferência do payload final; aprovar/rejeitar (com motivo) pelo drawer.
- **Baseline visual**: `toHaveScreenshot` por tela; snapshots gerados no Linux do CI e commitados em `frontend/e2e/__screenshots__/` — cada onda fechada adiciona os seus. Isto resolve a questão aberta do PRD sobre onde guardar o baseline.
- **Gate de conformidade**: verificação automatizada que falha se cor literal (hex/rgb/oklch, `bg-[#…]`, `style` com cor) aparecer fora de `styles.css`.
- CI: o job `test` ganha o passo Playwright e passa a rodar `npm run test:coverage` (aplicando os thresholds de 80% que hoje existem mas não são verificados).

Vitest/RTL continua sendo a camada principal de comportamento de componente.

## Alternatives Considered

### Alternative 1: Vitest + capturas manuais

- **Description**: Nenhuma infra nova; conferência visual manual contra os HTMLs de referência, capturas commitadas à mão por onda.
- **Pros**: Zero custo de infra; sem flutuação de rendering entre máquinas.
- **Cons**: Chamada offline nunca testada num navegador real; baseline depende de disciplina manual; regressões visuais silenciosas entre ondas.
- **Why rejected**: O usuário escolheu verificação mais forte; a chamada offline é o coração do produto e merece e2e real.

### Alternative 2: Playwright full-stack (backend + Postgres no CI)

- **Description**: e2e contra o sistema completo via docker compose no CI.
- **Pros**: Fidelidade máxima, cobre contratos reais da API.
- **Cons**: CI muito mais pesado e lento; seed de dados e autenticação por cookie httpOnly a orquestrar; flakiness de infraestrutura; foge do escopo (a iniciativa não muda backend nem contratos).
- **Why rejected**: A iniciativa é 100% frontend com contratos congelados — mockar a API testa exatamente o que muda, sem custo de orquestração.

## Consequences

### Positive

- A paridade offline (critério de saída da Onda 2) vira teste executável, não conferência manual.
- Baseline visual reproduzível e versionado, com diffs revisáveis em PR.
- A métrica nº 1 do PRD (zero cor literal) vira gate de CI desde a Fase 0.

### Negative

- Nova devDependency pesada (browsers) e passo de CI mais longo (~minutos).
- Screenshots dependem de rendering do chromium/Linux — devs em macOS precisam atualizar snapshots via CI (ou container), não localmente.

### Risks

- **Flakiness de screenshot** (antialiasing, fontes). Mitigação: chromium fixo, `maxDiffPixelRatio` tolerante a antialiasing, fontes de sistema (o DS não carrega webfont — rendering estável por construção).
- **Mocks derivarem dos contratos reais**. Mitigação: fixtures tipadas com os mesmos tipos TS de `src/types/` usados pelo app; contratos não mudam nesta iniciativa por non-goal.

## Implementation Notes

- Estrutura: `frontend/e2e/*.spec.ts`, `frontend/playwright.config.ts` (webServer: `vite preview`), fixtures de rota em `frontend/e2e/fixtures/`.
- O gate de cor literal roda como teste Vitest (varredura de `src/` com allowlist = `styles.css`) para ficar dentro do pipeline existente.
- Playwright instala só chromium no CI (`--with-deps chromium`).
